# 阶段性实现审查

审查范围为实施分支的 W1–W3、I1 及 W4 协议探针；完整产品仍停在流式恢复修订和真机安装关卡。独立审查以新上下文只读检查代码，并复跑了当时的 17 项 Node 测试与类型检查。

审查发现三项 Important 问题，无 Critical 或 Minor。作者已在一次修复过程中逐项复现失败，再修复并运行完整测试。

| 问题 | 修复与验证 |
| --- | --- |
| 两个启动者同时回收旧锁时，后者可能删除前者的新锁 | 通过独立回收锁串行核对旧所有者；确定性交错测试由并发进入数 2 变为 1，两次启动复用同一进程 |
| 服务 RPC 异常时无法显式停止自有进程 | 进程归属核验与 RPC 就绪分离，任务清单尽力读取；不可读取时提示后沿用停止确认，仍拒绝错误实例 ID 或已变更的进程身份 |
| 快照回调失败后仍分发缓冲中的增量帧 | 已失败/关闭的 RPC 客户端立即忽略后续帧；真实本地 WebSocket 回归由错误分发 1 次变为 0 次 |

修复后 `npm test` **21/21**、`npm run typecheck` 成功，Pester 5.7.1 启动器测试 **2/2**。额外真实 Windows 试验中，仅对受控自有测试服务移走令牌文件：状态仍返回正确实例/进程及 `tasksAvailable:false`，停止脚本提示任务清单不可用，并在明确停止意图下成功结束该实例。

回收锁的 `start.lock.recovery` 若在持有进程崩溃时遗留，启动器会报告检查锁所有者，不自动递归回收另一层锁。这样保留单实例保证，代价是该罕见恢复中断需要人工核查。检查 `stateDir` 内的锁记录和对应 PID，确认没有启动者仍在运行后再处理遗留锁；不要凭服务不可用就删除正在使用的锁。

iOS 编译、签名和设备状态见[签名验证记录](signing.md)，真实协议结果见[接管报告](live-attach.md)。审查没有把未实现的 SQLite/API/完整 iOS 界面、未测试的 MCP/权限/排队等能力、物理安装或非基线环境评为通过。针对非助手消息、被中断消息的完整恢复仍需各自验证。
