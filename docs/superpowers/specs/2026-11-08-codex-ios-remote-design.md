# Windows Codex CLI 的 iOS 远程客户端设计

日期：2026-11-08。状态：用户已确认完整方案，进入实施规划；尚未进入产品实现。独立审阅没有需要补问的关键问题。协议与真机可行性仍未实测。

## 1. 目标与使用场景

用户在 Windows PowerShell 中启动 Codex，任务开始后离开电脑，在 iPhone 上查看同一任务的执行进度、追加指令、回答问题、处理审批及查看文件差异；回到电脑后继续使用 CLI。

接管的对象必须是同一个运行服务中的同一条 thread 和当前 turn。仅复制历史、分叉或另起进程恢复记录，不能作为实时接管成功的证明。

功能参考 [codex-android](https://github.com/hebo6/codex-android/blob/master/README.md)。重写 iOS 平台实现，保留可复用的协议语义和业务行为；本设计不要求首版完整移植全部 Android 功能。

## 2. 用户已明确的约束

- 个人自用，原生 iOS App；不采用 PWA。
- 任务在 Windows 原生 PowerShell 运行；WSL Ubuntu 不参与首版。
- 网络采用 EasyTier；用户的 iPhone 已安装其客户端。
- 用户接受专用 PowerShell 启动命令，让 CLI 连接共享 app-server。
- 使用普通 Apple 账号；接受免费签名七天有效期及自动续签方向。
- Windows 开发，GitHub Actions 的 macOS 环境编译；Windows 本地签名和安装。
- 不做锁屏远程提醒，不集成 Bark 或其他通知客户端。
- 用户希望定时维护在 Codex 中完成。调度优先使用桌面端本地定时任务，具体频率和时区未指定，设计阶段不创建定时任务。

| --- | --- | --- |
| iPhone 客户端 | Swift、SwiftUI、iOS 16.0+ | 原生客户端；采用系统组件，首版不依赖需要更高系统版本的持久化框架 |
| 客户端通信 | URLSession WebSocket、Codable、Swift Concurrency | 系统能力足以实现事件流和状态同步 |
| Windows 桥接 | TypeScript、受支持的 Node.js LTS、PowerShell 启动脚本 | 接近 app-server 的 JSON 协议及生成的 TypeScript schema，方便诊断 |
| Codex 兼容基线 | 先锁定已检测到的 CLI 0.167.0 | 先验证当前安装，升级后才扩大兼容范围 |
| 持久化 | iOS Keychain 存令牌，普通配置与草稿使用本地文件；桥接使用 SQLite | 凭据与界面缓存分离；支持事件去重和发送结果核对 |
| 首版连接 | 可保存多个服务端配置，同一时刻连接一个；首要目标是一台 Windows | 个人使用，保留参考项目的多服务端扩展方向 |

## 4. 系统职责与连接

### Windows 共享 Codex 服务

在当前用户会话中运行一个项目可识别的共享 app-server，拥有任务、进程、shell 工具与原始会话历史。监听只用于本机访问的地址，开启 capability-token 认证。CLI 与桥接程序都连接这个实例。

首版使用独立、受管理的 app-server 实例作为可控基线，不要求连接当前不可达的默认 daemon，也不自动重启桌面 App 或已有任务。使用原有 Windows 用户的 Codex 配置与登录，避免要求 iPhone 保存 OpenAI 账号凭据。

### PowerShell 启动器

提供暂名 `Start-CodexRemote` 的命令：检查版本、共享服务身份与健康状态，在不存在本项目服务时启动它，然后用 `codex --remote` 加入。保留调用目录与参数边界，复用现有服务；不同目录下多次调用不应启动多个竞争实例。采用进程参数数组传参，不拼接执行任意命令字符串。

首次配置后的任务由这个命令启动。接入前已经在独立进程运行的旧任务，不承诺热迁移：可读取可用历史；需要继续时，应先让原任务结束或明确停止，再在共享服务中按同一 thread 恢复，避免两个运行者同时修改项目。正在执行的旧独立任务不得被自动结束、复制执行或悄悄当作已接管。

### Windows 桥接程序

桥接是共享服务的一个长驻客户端。它向 iPhone 提供经过认证的业务接口，保存事件投影、待处理请求及发送核对信息，隔离 iOS 对实验性协议的直接依赖。

对 Codex 的会话创建、读取、续接、追加、中断和审批请求进行明确映射；桥接 API 不提供一个额外的、不受 Codex 策略约束的通用 shell 执行入口。CLI 继续由原生 TUI 驱动，不解析终端文本来推测状态。

服务端保留真实状态权威。桥接记录带版本的状态快照和递增事件游标，供手机同步；不能因自己的缓存存在就把已经失效的审批或执行状态当作当前状态。

### EasyTier 与 iOS

手机使用现成 EasyTier 客户端，iOS App 连接 Windows 虚拟 IP 上的桥接入口。默认入口只绑定 EasyTier 地址，采用服务端配对令牌，并限制 Windows 防火墙访问范围。首版采用 EasyTier 加密隧道内的 WebSocket，iOS 对此入口配置所需的最小网络权限；是否需要更窄的 ATS 例外须真机验证，不默认开放任意网络请求。若真机或部署条件要求 TLS，改为本机可信证书的 WSS 并确认信任，不关闭证书校验。

安装与首次配对通过明确填写地址和令牌完成，扫码可作为后续易用性增强。iPhone 不访问 Windows 的全盘文件系统。

## 5. 首版建议范围

| 能力 | 首版行为与边界 |
| --- | --- |
| 服务端配置 | 保存、编辑、删除和切换连接；令牌放 Keychain；显示连接和版本状态 |
| 项目与会话 | 按项目目录组织，查看运行中与历史任务，搜索、恢复、重命名及归档；支持在已配置的项目中新建任务 |
| 流式过程 | 展示用户和助手消息、协议提供的计划/推理摘要、命令输入输出、工具活动、任务状态；不承诺获取模型隐藏推理 |
| 输入 | 文本、草稿、运行中追加指令、下一回合排队及明确中断；操作结果以服务端确认显示 |
| 审批与提问 | 命令、文件、权限、用户问题及受支持的 MCP 确认；只提供服务端实际允许的选项 |
| 文件差异 | 按文件查看该回合累计 diff、命令输出与执行状态；首版以只读审阅为主 |
| 子代理 | 显示协议提供的子任务状态、打开子会话并返回父会话 |
| 基本设置 | 查询可用模型与推理强度；沿用服务端权限策略，前台可查看当前配置 |
| 前后台切换 | 前台实时更新；后台允许断开；重新进入时同步真实状态、结果和待处理请求 |

后续阶段再补：图片和文件上传下载/分享、会话分叉/删除、额度详情、Skills/Apps/Plugins/MCP 管理、完整终端输入、快捷短语和更多配置项。已安装 Skills、MCP 等仍由 Windows Codex 自己执行，首版不以缺少手机管理界面禁用它们。

用户已确认该首版范围及后续功能划分；后续功能保留为扩展方向，不将参考项目的全部能力都算作首版已实现。

## 6. 同步、竞争与生命周期

- 使用 `(serverId, threadId, turnId, itemId)` 识别状态对象，增量文本按事件顺序合并，重放去重。
- 手机加入已有任务时，先获取快照和游标，再续订事件；快照期间发生的事件需要补齐，不能只从连接成功后开始显示。
- 断线后按游标补发；游标失效、桥接重启或原始历史无法补齐时，丢弃过期投影并重新读取服务端历史与运行状态。界面显示正在同步，不显示伪造的完整性。
- 手机每次写操作带客户端操作 ID，桥接记录提交状态和上游结果。超时后先核对状态；不能盲目重发 `turn/start`、审批响应或其他副作用操作。不能确认的操作显示“结果待核对”，交给用户判断。
- 并发输入以共享服务确认为准，不创建两个同时运行的 turn。运行中输入区分当前回合 steer 和下一回合 queue；上游不支持 queue 时先使用客户端草稿，明确显示尚未提交，不伪称服务端排队。
- 审批响应绑定当前请求、thread 和 turn，CLI 或手机任一端处理后同步失效状态。桥接只对已知、仍有效的请求转发一次决定；竞争导致过期时显示“已处理”，不重新执行。
- 首版不引入独占控制锁，CLI 与手机均可输入。用户已接受共享启动方式；需要通过双端测试验证服务端实际竞争语义。
- 手机进入后台或失去网络后，Windows 共享服务继续承载任务；等待人工审批时保留等待状态，用户重新打开后再处理。没有锁屏提醒或持续后台保活承诺。
- 正常关闭 CLI 窗口不应停止共享服务；显式停止服务会中断正在执行的工作，必须单独说明。电脑睡眠或断电期间没有继续执行保证；不自动修改电源策略。

## 7. 实现之前的技术验证关卡

设计确认后，先做有限范围的验证，再决定完整实现计划的后续细节。不要以文档中的接口名称代替验证结果。

1. 在 Windows 上用 0.167.0 建立带认证的共享服务，并由原生 CLI 连接。使用独立的临时测试项目和测试任务，不操作用户真实任务。
2. 在 CLI 发起一个有明显持续进度的回合；第二个协议客户端中途加入，核对同一个 thread、turn 和实时输出。不得通过分叉或重复运行达标。
3. 在第二客户端加入前制造一个待审批/待回答请求；验证加入后能否获取并合法响应。再验证两端同时可见、任一端完成后另一端失效。
4. 验证追加指令、中断、排队能力以及两个客户端竞争响应的处理结果。
5. 断开第二客户端、退出 CLI 界面，再连接，验证任务继续执行、状态补齐和请求不会重复触发。
6. 通过 EasyTier 做 iPhone 到 Windows 的真机连通性和网络权限检查；不要把 VPN 存在等同于桥接端口已可达。
7. 云端构建最小真机版本，在 Windows 用普通账号签名安装；验证重签覆盖安装后草稿、配置与 Keychain 访问保持一致。

关卡 2、3 或 5 失败时，停止宣称“实时接管可行”，先报告实际缺口。可研究桥接代理路由或有限的上游改动，但那是新的架构决策，需要修订设计；不会静默更换 CLI、使用终端抓取或切换成新的独立任务。

本机现有证据仅证明版本和命令存在。默认 daemon 控制套接字连接失败，尚未验证上述关卡。命令参数、schema 和审批广播/重放规则以锁定版本生成的 schema 与实际行为为准。

## 8. 构建、安装与续签

GitHub Actions 在 macOS 上编译不含账号凭据的 iPhone 真机应用，关闭构建期签名；按标准 Payload 结构打包未签名 IPA，作为私有构建产物供 Windows 下载。需要真实设备架构，不能拿模拟器产物代替。最初用最小 App 验证该产物可由本地工具签名，不把未经验证的 archive/export 参数当作现成流程。

在 Windows 用 Sideloadly 和用户自己的普通 Apple 账号完成配对、签名及安装。首次安装由用户完成必要的信任、验证和 iOS 开发者模式操作。Apple 凭据留在本地签名工具，构建仓库和 Actions 不需要保存它们。使用稳定 Bundle ID，重签和更新采用覆盖安装；不默认卸载应用。

配置 Sideloadly 内置自动 refresh。它在手机经 USB 或已配置的同一局域网 Wi-Fi 可达时执行实际续签；EasyTier 网络互通不等于已经支持 Apple 设备发现、配对和远程重签。离开续签电脑超过免费期限的场景仍可能到期。

按用户最新偏好，维护调度放在 Codex 桌面端的本地定时任务中。建议任务仅执行已测试的维护脚本：检查 Sideloadly 后台进程、缺失时在当前用户会话中启动、检查可获得的结果证据并记录状态。启动 GUI/后台工具使用隐藏窗口及固定路径，不为本项目强制终止现有签名进程。具体脚本与时间表在实现阶段测试后配置。

Codex 本地调度需要电脑开机、桌面 App 运行，纯 CLI 没有对应的调度管理界面。每次模型运行可能占用账号用量；维护频率不需要跟随任务事件高频执行。若没有可读取的续签成功证据，报告“已启动/等待设备/无法确认”，不得报告“续签成功”。需要手动 Apple 验证时明确留下待处理状态，不尝试绕过验证。普通账号仍然是每次七天，而非延长单次有效期。

不在设计阶段安装 Sideloadly、配置 Apple 登录、创建定时任务或触发 GitHub 构建。具体执行时间与时区后续由用户确定。

## 9. 最低验证与交付要求

- 协议/桥接测试覆盖乱序与重复事件、断线补齐、超时后核对、重复审批、过期请求和服务重启；使用真实协议样例及受控集成测试。
- 真机验证服务端配对、EasyTier 连通、流式显示、文本输入、审批、diff 和前后台恢复；不以模拟器或 TypeScript 单测代替 Windows/iPhone 双端验证。
- 验证多个 PowerShell 启动器复用一个服务，工作目录正确；手机离线不会自动拒绝审批或丢失任务。
- 验证免费签名安装、覆盖更新、至少一次真实续签，分别记录实测与未实测项。
- 交付 iOS 源码、Windows 桥接及启动器、CI 配置、可签名 IPA、安装/续签/诊断说明；这些属于设计批准后才执行的工作。

成功标准是用户能从已通过专用启动器发起的任务中途接入，并在同一任务上完成至少一次指令追加和审批处理；两端结果一致。首版不以模拟数据、历史只读浏览或新建另一条任务冒充成功。

## 10. 已知限制与非目标

首版不做云端多用户平台、团队权限、PWA、第三方通知、APNs、WSL 支持、越狱能力、签名期限绕过、自动迁移独立运行中的旧任务，或全盘远程桌面。原生客户端未来可增加通知能力，但本次方案不以付费开发者账号为前提。

WebSocket 传输由上游标记为实验性；绑定一个已验证的协议版本，升级先验证后启用。旧版本或不支持的功能显示明确状态，不静默更改权限策略。
